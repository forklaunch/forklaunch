# Base IAM identity integration

## Sessions, key publication, seeding and CORS

`RsaJwtSessionIssuer::from_env` reads `SESSION_JWT_PRIVATE_KEY_PEM` (PEM verbatim or base64 of the PEM on one line), `SESSION_JWT_KEY_ID`, `SESSION_JWT_ISSUER` and `SESSION_JWT_AUDIENCE`. `RsaJwtSessionIssuer::jwks()` returns the public JWK set (`n`, `e`, `kid`, `alg: RS256`, `use: sig`); `IamHttp::with_jwks` serves it at `GET /api/auth/jwks`, the URL generated `JWKS_PUBLIC_KEY_URL` settings point at.

The legacy bearer routes `GET /users/:id` and `/users/:id/permissions` return only the caller's own record unless the session holds `platform:read` (`http::ADMIN_READ_PERMISSION`); `GET /users` and `GET /organizations` always need it. Other callers get 403.

`IamHttp::with_cors_origins` admits exact browser origins with credentials; without origins no CORS headers are sent and `*` is never emitted.

The `seed` feature adds `seed::SeedConfig`: roles and login users from TOML, applied idempotently through `AsyncIamRepository` with passwords read from the variables each user names. `SeedConfig::apply_directory` then writes the directory records `POST /user` would create (permissions, roles, organizations and a directory user under each login id), idempotently, so seeded users surface roles and pass organization-scoped directory routes. Directory `createUser` keeps ignoring passwords, as the TypeScript iam-base mapper does.

Directory CRUD and credential/provider users remain independent unless an authorized administrator explicitly links existing identities. `PostgresDirectoryStore::bind_auth_identity(directory_id, auth_user_id)` creates a tenant-local, one-to-one association and an actor/correlation audit in one transaction. Repeating the same pair is idempotent. Email, profile fields, passwords, organizations and grants are never copied or used to infer a link. Directory create/update mappers continue to ignore passwords.

`PostgresIamService::directory_user_for_session(token)` accepts the **complete issued session token**, including the complete JWT when RS256 issuance is configured. It hashes the token and requires a current persisted session, an enabled credential user and a current directory binding in the same tenant. A user ID, JWT subject, arbitrary session ID or independently signed JWT is insufficient. Expired, revoked, disabled and foreign-tenant sessions return `None`. This lookup supplies an identity association; applications must still authorize directory operations and resolve current directory grants.

`unbind_auth_identity(directory_id, expected_auth_user_id)` removes only the exact current association with an atomic audit. Independent credentials, provider mappings and sessions remain valid, but those sessions cease resolving a directory identity. Ordinary directory deletion, including compliance erasure, is restricted while the identity is bound. Authorized administrators can instead use `delete_linked_identity(directory_id, expected_auth_user_id)` to atomically delete the credential user, cascade all persisted sessions/provider mappings, and delete the directory identity and uniqueness claims with audits. Any failure rolls the entire operation back. Deleting a credential user through the existing API also cascades its association and sessions while retaining the independent directory profile.

These methods are administrative library APIs, not public self-service linking endpoints. The caller must authorize the administrator and construct a trusted tenant-bound store with an `AuditContext` containing a nonblank trusted actor ID and correlation ID. Missing/blank actors are rejected by these three administrative methods; ordinary directory CRUD keeps its existing audit policy. The three new administrative APIs record their mutations in the existing directory audit table. Legacy `PostgresIamService::delete_user` has no audit context: its foreign-key association cascade retains the existing unaudited deletion semantics. Resolving an association does not create an administrative audit event.

Migration `0006_directory_identities.sql` must run under the schema-owner connection. Runtime roles using the new association APIs need the following additional grant (replace `iam_runtime` with the application's restricted runtime role):

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON fl_iam_directory_identities TO iam_runtime;
```

Existing directory/auth table and audit grants remain required. The new table enforces tenant RLS and composite foreign keys; runtime roles must not have SUPERUSER or BYPASSRLS. Default CRUD/auth APIs do not query the association table. Generic custom mapper/filter behavior and automatic directory authorization integration are separate work.

Opt-in directory authorization uses `PostgresDirectoryStore::authorization_for_session` to read the binding, enabled credential user, live persisted session, current directory role names, permission slugs and organization in one transaction. It holds shared directory and ordered user/session locks while hydrating that snapshot. Read audits use the verified directory identity. Results are never cached; a grant edit affects the next request even when the token was issued earlier. The configured TypeScript surfacing helpers use the same literal names/slugs and set semantics but cache by user; this native mode deliberately reads fresh.

`IamHttp::new` (`http` feature) selects `DirectoryAuthorizationMode::StoredSessions` explicitly. Existing directory JWT routes first verify the complete JWT through trusted JWKS, then replace the subject and all grants with the persisted snapshot **before** framework role/permission checks. Organization-scoped user operations use that same snapshot's organization. A signed but unpersisted token, missing binding or disabled/revoked/deleted identity fails closed. Legacy bearer endpoints and internal HMAC operations keep their existing policies. This option does not implicitly authorize browser-cookie requests or accept opaque tokens on JWT routes.

`BaseIamDirectory::unit_of_work()` exposes a caller-owned directory transaction. Its `create`, `update`, `get`, and `delete` methods use sealed `Permissions`, `Roles`, `Users`, and `Organizations` markers with each family's existing DTOs. Multiple related operations see their staged writes and commit together; dropping the unit rolls back. Failed operations, failed mapper projections, canceled futures, and mapper panics poison the unit, so catching a failure cannot commit earlier writes. Tenant binding, the store's audit actor/correlation, organization scope, encryption, relationship rules, explicit identity deletion restrictions, and ignored password fields remain enforced.

Applications implement `DirectoryMapper<Family>` to accept custom create/update types, asynchronously project custom outputs, and pass an explicitly typed application context. Create/update hooks receive the same typed unit of work for related operations. `mapped_create`, `mapped_update`, and `mapped_get` apply these hooks around core mapping. Hooks receive no SQL connection or tenant override. The extension maps to existing entity families and supported `providerFields`; it does not provide arbitrary custom tables, arbitrary filters, or credential linking. The actual TypeScript service fixture verifies custom projections and caller `EntityManager`/flush behavior; TypeScript permission updates omit extra arguments, while the native adapter consistently accepts its typed context.

The unit of work also exposes `list::<Family>(ids, filter)` and `mapped_list`. `DirectoryFilter` uses a sealed field enum per family and supports `All`, `Any`, `Not`, scalar `Eq`/`Ne`/`In`/`NotIn`/`IsNull`/`IsNotNull`, and explicit related-ID existence. Only declared string fields, UUID IDs/FKs and role/permission relationships are admitted; arbitrary JSON paths, SQL, dates, range/pattern operators, custom properties and relation traversals are not supported. UUID predicates/selectors accept canonical hyphenated spelling in either case; ordinary strings remain case-sensitive. Missing nullable properties behave as SQL NULL, including UNKNOWN under ordinary negation. Empty IN matches none; empty NOT IN matches all, including null. Empty AND matches all and empty OR matches none. Nested empty groups follow actual MikroORM SQL-fragment normalization: an empty AND is omitted even inside OR, so `Any([All([]), predicate])` matches the predicate; negating an omitted group matches none. Tenant and organization restrictions remain outside these predicates. Unsupported fields/operators and excessive predicate budgets are rejected before reading rows.

Predicate validation happens before reads: maximum depth 16, 256 nodes, 4096 values and 64 KiB total literal bytes. Evaluation has a shared one-million-operation budget. Tenant and trusted organization scope are mandatory outside the expression, including OR/NOT. Candidate reads retain existing insertion order and deduplicate selector IDs; no pagination or custom sorting is introduced. At most 4096 candidate rows are allowed, and overflow returns `iam_directory_scan_limit` instead of a truncated result. Predicates evaluate on decrypted tenant-local rows and audit candidate reads even if they do not match; related DTO hydration adds its existing reads. This has application-memory/decryption/audit cost and is not an indexed SQL query planner. Evaluation exhaustion returns `iam_directory_filter_limit`; either limit poisons the unit of work. Actual MikroORM/PostgreSQL comparisons cover the admitted subset, not arbitrary `FilterQuery` parity.
