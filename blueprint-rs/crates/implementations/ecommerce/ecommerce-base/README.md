# Ecommerce durable provider scope

With `postgres`, `PaymentProviderScope::administrative` and `PostgresEcommerceStore::provision_payment_provider_binding` record an explicit trusted administrator assertion tying a tenant's durable payment to a provider, deployment, merchant/account, mode, reference, order, amount and currency. Provisioning compares the supplied payment snapshot to the locked durable row and requires its order to exist. It never reads a key prefix, infers ownership from provider fields, contacts a provider, changes a payment, or backfills existing rows.

Migration 9 adds bindings and audit tables without changing migrations 1–8, records, encrypted addresses, existing reconciliation audits or provider references. Bindings last until explicit generation-checked revocation or deletion of their associated payment/order. Deletion cascades the binding, so recreating identical records cannot revive it; historical audit records remain. Status/timestamp changes may retain a binding, while reference/order/amount/currency changes deny reads. Changes restored on the same existing record may match again; this is an administrative relation assertion, not a historical record-version proof. Later effect workflows must independently lock and compare current payment/order snapshots and the binding generation.

Administrative operators need `SELECT, INSERT, DELETE` on `fl_ecommerce.payment_provider_bindings`, `SELECT, INSERT` on `fl_ecommerce.payment_provider_binding_audit`, and existing record `SELECT, UPDATE` permissions for row locks. Do not grant these automatically to default application routes. All tables force tenant RLS. Audit RLS permits only INSERT/SELECT even when a non-bypass role has broader table grants. Provision/revoke require a nonblank actor and correlation; audit failure rolls back the binding change. Database owners remain trusted and can alter policies or data.

`payment_provider_binding` returns an opaque generation under a matching trusted scope and current local relation. It is neither a verified provider context nor permission to mutate money. It does not replace tenant authorization, prove the current merchant/API-key binding, enforce provider mode remotely, or authorize reference clearing, refund, capture, cancellation, order reopening or event replay. The separate [Stripe direct/connected operator flows](../ecommerce-stripe/README.md#cancelled-order-terminal-repair) and [PayPal VOIDED operator flow](../ecommerce-paypal/README.md) authenticate short-lived provider evidence and atomically recheck scope, generation and record snapshots with their audits and receipts. Their admitted terminal cases are described in those guides. Both flows retain provider references; broader ambiguous or charged cases still require review.

`PaymentResumeStore` adds a read-only current payment/order relation check. The memory adapter checks under its record lock; PostgreSQL uses one tenant-scoped statement selecting no order address. `StripePaymentService::resume_payment_for_order` invokes it before and after retrieving a client secret, and the generated ecommerce checkout backend uses that guarded API. Missing/mismatched identities or cancelled orders deny the response; other known order statuses retain existing behavior. References and provider state are unchanged. Generic `resume_payment` remains the explicit legacy path for custom integrations. These checks do not revoke a secret already issued or prevent cancellation after the final check; they do not prove provider-terminal cancellation or authorize any monetary action.

Migration 10 adds `scoped_payment_cancellation_receipts` without changing previous migrations, old cancellation timestamps, ciphertext, or administrative bindings. The table uses tenant SELECT/INSERT-only RLS; it retains the binding generation, account/mode/deployment, order version, terminal evidence and actor/correlation alongside the existing cancellation audit. It has no public HTTP endpoint. Trusted operator credentials need SELECT/UPDATE on records and provider bindings for row locks, UPDATE on the payment record, SELECT on capture history, and INSERT on both cancellation audit/receipt tables (plus SELECT on receipts for outcome inspection). The normal read-only inspection profile requires no added write grants. The store API accepts already verified evidence and a freshness callback from trusted code; it does not independently contact Stripe or grant ownership. Lock order is payment → order → binding, matching provisioning; revoke only locks binding. Do not introduce callers that acquire those locks in reverse order.

`record_scoped_cancelled_order_cancellation` compares the exact sealed payment/order/binding snapshot and retains references while marking only the payment failed. Ordinary validation/audit failures explicitly await rollback. COMMIT transport errors or task cancellation may still be ambiguous, so retain the supplied receipt UUID and use the tenant-scoped receipt query. A successful commit followed by deadline expiry is returned as `RecordedEvidenceNoLongerCurrent`, not as a rollback. No payment/order data or financial operation can be replayed from the receipt.


Migration11 adds tenant SELECT/INSERT-only scoped capture receipts linked to
existing reconciliation audits. `captured_payment_snapshot` selects no order
address; `record_scoped_capture` locks payment → order → binding and compares
exact payment body/order xmin/binding generation before atomic succeeded status,
audit and receipt. Retained cancellation history blocks adoption even if order
status was restored. This trusted store API accepts authenticated evidence from
the operator adapter; it makes no provider request or settlement guarantee.
Operators need existing record/binding lock/update grants, capture/cancellation
history SELECT and reconciliation-audit/receipt INSERT, plus receipt SELECT for
ambiguous COMMIT inspection. No default application grant is widened.
