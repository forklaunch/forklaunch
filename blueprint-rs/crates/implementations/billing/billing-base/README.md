# Billing persistence

With the `postgres` feature, `PostgresBillingStore::migrate` applies migrations using a schema owner. Runtime stores require a separate role without SUPERUSER/BYPASSRLS and an explicit tenant. Sensitive provider fields and session URLs remain encrypted; plaintext reads require an audit context.

Migration 5 adds an administrative Stripe identity foundation. `StripeBindingScope::administrative` explicitly names the deployment label, account ID and live/test mode. This is trusted server configuration: this constructor does not authenticate this scope, and API key prefixes or client-provided `providerFields` must not supply it.

`provision_stripe_binding` requires an existing durable checkout, payment-link or portal record, an explicit public UUID, provider reference, and nonblank actor/correlation context. It preserves existing storage keys and encrypted fields. Cache-only ownership is rejected. Public, storage and scoped provider references cannot be duplicated. `stripe_binding_by_public_id` and `stripe_binding_by_provider_id` require the exact tenant/account/mode/deployment/kind context. `revoke_stripe_binding` accepts the opaque generation returned by provisioning or lookup; a stale generation cannot revoke a replacement. Provisioning and revocation commit with their audit records.

Grant the administrative role schema USAGE, SELECT/UPDATE on `fl_billing.records`, SELECT/INSERT/DELETE on `fl_billing.provider_bindings`, and SELECT/INSERT on `fl_billing.provider_binding_audit`. UPDATE on ownership records permits `SELECT ... FOR UPDATE`. The audit table has only tenant-scoped SELECT/INSERT RLS policies, so non-bypass runtime roles cannot update or delete audit rows even with broader table grants. Schema owners retain normal administrative control. Revoke the binding before deleting its durable record; the foreign key intentionally restricts deletion while an alias exists.

These APIs expose no HTTP route, make no provider calls, and perform no automatic migration/backfill. Existing service wrappers, webhooks and checkout reconciliation still use their original IDs. Binding lookup results are snapshots, not financial-operation capabilities. Scoped provider reads use separate opt-in APIs; subscription authenticated reads, cache ownership/expiry and portal replacement remain separate work; the foundation alone does not establish runtime TypeScript/Rust identity parity.

Migration 6 extends durable bindings to subscriptions without changing existing aliases, record keys, ciphertext, or prior migration history. Use `StripeSubscriptionOwnership::administrative` to explicitly assert the provider customer (`cus_…`) and local party ID/type, then `provision_stripe_subscription_binding` with the public UUID, durable storage ID and provider subscription (`sub_…`). Provisioning requires the locked local row's `externalId`, `partyId` and `partyType` to match these inputs. The generic `provision_stripe_binding` deliberately rejects subscriptions lacking this relation. Provisioning decrypts/audits the owned row, so its role also needs INSERT on `fl_billing.sensitive_read_audit`.

The customer relation is an administrative assertion, **not authenticated Stripe ownership evidence**. These methods make no HTTP calls. A later authenticated provider read must compare Stripe's customer exactly with the asserted provider customer and verify account/mode separately; local party IDs need not equal Stripe customer IDs. `providerFields` never supplies ownership. Reads reject changed local ownership or changed/replaced binding relations, and revocation retains generation checks. No subscription wrapper, webhook repair, provider mutation, automatic alias backfill, or receipt completion is enabled by this foundation.

Paused subscription bookkeeping is a separate trusted operator API. `inspect_paused_subscription_effect` requires an inactive local row, exact durable subscription ownership, and an inactive matching attempt. `acknowledge_paused_subscription_effect` compares row and binding versions, checks the caller's authenticated-evidence callback after awaited locks and before COMMIT, then atomically writes the reconciliation audit/receipt and removes the attempt. It never writes the subscription. Grant this operator UPDATE on `provider_bindings` as well as `records` for PostgreSQL `SELECT FOR UPDATE`, INSERT on sensitive/reconciliation audits and receipts, and SELECT/DELETE on attempts. These are explicit trusted operator permissions, not default runtime grants.

The store does not authenticate Stripe. Use the Stripe wrapper for evidence checks; a callback that always succeeds is only appropriate for a separately verified trusted workflow. A post-COMMIT failed evidence check returns `RecordedEvidenceNoLongerCurrent`: the receipt was written, and rollback is no longer possible. No API promises the actual durable COMMIT instant fell inside the evidence window. COMMIT errors, timeouts, or cancellation can be ambiguous; query `paused_subscription_effect_receipt_recorded` before further action. This acknowledges an already-satisfied local effect, not callback causality or an uninterrupted provider pause epoch.
